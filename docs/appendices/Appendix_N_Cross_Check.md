# Appendix N implementation cross-check

The supplied draft is not an accurate description of the current implementation. The corrected appendix contains **35 functional modules and 157 function rows**. It adds implemented workflows, removes unsupported direct actions, distinguishes staff records from client-facing views, and flags access discrepancies instead of presenting them as approved permissions.

The review covers the local working tree at commit `26f9475c24cbad138950d203fe171c391d3fd243`, inspected on 6 September 2026. It does not establish what version is deployed. Programmer assignments are intentionally unspecified. Every “No. of Points” value is blank. The supplied image controls the table appearance; its example module names, users and point values are not requirements for this system.

## How to interpret the appendix

An asterisk means an implemented action or access path, subject to the accompanying notes. Empty cells mean no listed access for that specific action. The System column identifies automatic processing, not a login role. A user receiving an email does not have a “send email” permission. An exclamation mark identifies a source-confirmed access discrepancy, not an approved permission.

Public routes are not OFW-role gates. A staff user can reach public tracking, intake and survey routes, but must still satisfy the same email, OTP, session or invitation requirements. Conversely, a registered OFW can access account features unavailable to an anonymous visitor. Combining these two client identities in the original OFW column requires the qualifications in the appendix.

The count is a functional grouping for this appendix, not a count of database tables, controllers or routes. Related timeline displays are consolidated, as are the shared Activity Log / Audit Log implementation. Case lifecycle, intake review, document requests and administrative tools are separated where they have distinct actions and actor restrictions. Chart types and filters are functions within Reporting, not additional modules.

## Access discrepancies that must not be hidden by the table

These are findings about the current source. No application code was changed to correct them, and the focused test run below is not a complete security assessment.

1. **OFW report page.** `/reports` is in the authenticated/verified group. `ReportsFilterRequest::authorize` only checks for a user. `ReportsService::getAll` chooses its Case Manager payload for the default role, and `hasRequiredRoleScope` only requires an agency ID for AGENCY. Its query builders do not scope that default path to an OFW client. Report export differs: `ReportsExportService::extractCriteria` explicitly rejects roles outside ADMIN, CASE_MANAGER and AGENCY. Correcting the documentation alone cannot establish an OFW denial.
2. **OFW referral list, creation page and referral export.** The route group has no staff-role middleware. `ReferralController::index/create/exportExcel` have no equivalent staff-role denial. The list and export queries only special-case AGENCY. The creation submission is protected by `StoreReferralRequest::authorize`, and detail/mutation methods call their own access checks. Therefore “cannot create a referral” does not prove “cannot see the referral creation page or list.”
3. **Client-selection API.** `/api/clients` and `/api/clients/{client}` in `web.php` require auth/verification but have no staff-role gate. `ClientSelectController::search/show` exclude unaccepted intake records but do not impose actor role, agency referral or OFW ownership scope. Ordinary `/clients` pages have additional checks that do not automatically protect these API routes.
4. **Case Manager audit scope differs from comments.** `AuditLogController::scopedEntityIds` returns an empty array for both ADMIN and CASE_MANAGER. `buildFilteredQuery` skips the entity filter for an empty array. The Case Manager therefore has the unscoped query despite route comments describing “their cases.” Agency users with no agency receive a sentinel that matches no rows. Export still explicitly requires Administrator.
5. **Shared account endpoints versus portal screens.** The shared profile, MFA setup, email-change and onboarding endpoints are not staff-role-gated. The appendix records endpoint capability rather than claiming OFWs cannot reach them because their normal portal navigation does not link them. Whether those broader account capabilities are intended is a product-policy decision.

## Verification and limits

- `php artisan route:list --json` succeeded and registered **238 routes**. Registered routes, middleware, FormRequests, controllers, services, models, report components and relevant tests were cross-checked. Stale descriptive comments were not treated as stronger evidence than executable conditions.
- `npm run build` succeeded. It emitted the existing large-chunk advisory.
- A focused run of `ReferralAuthorizationTest`, `ReferralMilestoneTest`, `OfwRouteIsolationTest`, `ReportsAgencyScopingTest` and `CaseReferralGuardTest` passed: **37 tests, 79 assertions**. The first attempt had 5 failures caused by the absent Vite build manifest; rebuilding and rerunning the same suite resolved them.
- These tests verify selected referral access, milestone state behavior, OFW/staff route separation, agency report scope and case closure guards. They do not exercise every cell or demonstrate that the identified OFW report/referral/API discrepancies are blocked. Those discrepancies are conclusions from the inspected route-to-query source paths.
- The final PDF has nine Letter-size pages, plain black text and borders, repeated column headings, module headings with numbered functions, programmer placeholders and blank point values. Module blocks are kept together. The matching HTML contains editable source text and can be opened in a browser for copying or printing.
- A DOCX authoring intermediate exists, but the packaged Word renderer could not run because LibreOffice is unavailable. It is not the visually verified deliverable; use the delivered PDF for fixed pagination and the HTML for editable table content.
- The review does not verify production configuration, email delivery, every AI answer, every runtime route or all record-state combinations. Configured MFA roles, IP whitelist and enabled system settings can further qualify access.
